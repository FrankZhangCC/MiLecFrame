# GUI 代码质量报告二次审查

> 日期：2026-09-30。审查对象：`CODE_QUALITY_AUDIT_GUI.md`，并逐项对照当前源码与本地安装的 QFluentWidgets。
> 运行证据基线：HEAD `b64388f`；PySide6 6.11.1、PySide6-Fluent-Widgets 1.11.2、PyYAML 6.0.3。原报告的 `b3b375c` 已不是当前 HEAD。
> 交付范围：二审文档、独立探针及 JSON 证据；没有修改业务源码，没有执行重构、提交或发行。原报告 D1/D2/D3 保留，本文指出执行方案需要补充之处。

结论：**结构问题的大方向成立，但原报告不能直接作为执行清单。** G11 的删除建议会造成初始化崩溃；G10 漏掉相对定位控件未入布局的直接根因；还遗漏 PNG 导出失败和真实样式经 GUI 读写后改变引用的问题。因此“GUI 行为正确性大体可信”“这些问题不阻断发行”缺少足够证据，T1“零风险”也不成立。

## 1. 必须先修订的发现

### R1 / P1：G11 把初始化保护误判成无意义防御

原报告位置：G11、T1（原报告第 188–192、219 行）。

相机页 `__init__()` 第 89 行先调用 `_load_data()`，第 90 行才调用 `_setup_ui()`；`_load_data()` 第 106 行已经调用 `_refresh_table()`，而表格直到 `_setup_ui()` 第 155 行才创建。镜头页相同：第 125–126、142 行。

探针记录两页首次刷新时 `hasattr(page, '_table') == False`；只在内存中删除该保护分支后，两页构造都报 `AttributeError: ... has no attribute '_table'`。

**修订要求：** 从 G11/T1 删除“直接删除相机/镜头页保护”的动作。如果需要去掉检查，应先调整初始化顺序，或分离读 CSV 与刷新 UI；这是生命周期调整，要验证首次构造、首次显示和再次显示。主窗口关闭保护、样式页 resize 保护须分别判断，不能用“最终无条件创建”证明所有回调发生时属性都已存在。

### R2 / P1：G10 根因遗漏，单改 hide→disable 和刷新高度不足以修复

原报告位置：D1/D2、G10（第 29–39、180–186 行）。

`ElementEditor._setup_ui()` 第 167 行将 `abs_widget` 加入外层布局；第 170–247 行创建 `rel_widget` 和内部网格，却**没有调用 `layout.addWidget(self.rel_widget)`**。模式切换第 255–256 行只是切换可见性。

真实 Qt 控件探针结果：

| 卡片 | 切换前内容 sizeHint 高度 | 切换后内容 sizeHint 高度 | 切换后卡片高度 | 相对组实际几何 / sizeHint |
|---|---:|---:|---:|---|
| ElementsSection | 482 | 154 | 552（未刷新） | `100×30` / 高 243 |
| DefinedTextsSection | 521 | 193 | 591（未刷新） | `100×30` / 高 243 |

两张卡内 `editor.layout().indexOf(editor.rel_widget) == -1`。这不是报告所称的“8 行切 6 行、相差约两行”，而是相对组根本未参与布局。高度未刷新也存在，但它只是另一个问题。

**修订要求：** D2 必须显式包含将相对组加入布局，再落实 D1 禁用策略和容器高度刷新。不能宣称单靠 D1 就已“根除隐患”。验收还必须检查两组均在布局内、相对控件完整可见可操作，并检查子控件边界；只检查 `spaceWidget.h >= view.h` 会漏掉此缺陷，本次故障状态下这个不等式仍成立。

### R3 / P1：G2 只讨论导出流程归属，漏掉 PNG 导出确定失败

源码：`image_processing_page.py:1295`、`:1305–1307`；`output_metadata.py:758–760`。

导出副本固定命名为 `dst_path + '.part'`，但格式判断取这个临时路径的最后后缀。`out.png.part` 的后缀为 `.part`，于是 `expected_format` 总是 JPEG。验证器检查实际编码，PNG 被拒绝，单张与批量共用同一条故障路径。

探针先生成带生产元数据的 JPEG/PNG 并通过生产验证器检查源文件，再调用原有 `_export_verified()`：JPEG 成功；PNG 报 `OutputMetadataError: 输出实际格式为 PNG，期望 JPEG`，未发布目标。

**修订要求：** 增加独立正确性修复任务。格式应来自已知结果编码或源文件实际编码，不能从 `.part` 后缀推断；若允许用户更换目标后缀，还须明确重命名与转码的契约。验收必须同时覆盖 JPEG/PNG、单张/批量、失败时旧目标保留和临时文件清理。把原实现直接搬到服务层不会解决故障。

### R4 / P1：G1/§8 漏测真实控件往返，FilmClip 引用会静默改变

原报告位置：G1 验收、第 206、233、239 行。

`ELEMENT_KEYS`（`style_config_form.py:25–31`）只有固定键和泛称 `defined_text`，没有 `defined_text_01` 等实例键。`ElementEditor` 第 176 行用它创建 `relative_to` 下拉，第 331 行尝试恢复模型中的引用；不存在的选项无法选中，保存第 357 行写回当前默认选项。已有 `update_relative_to_options()`（第 415 行）没有调用点。

对全部 **14 个内置 YAML** 执行“模型 → 四张真实定位卡加载/保存 → 模型”，4 个文件产生变化：

| 样式 | 已确认变化 |
|---|---|
| FilmClip/default.yaml、no_custom_text.yaml | 四个 `info_position` 元素的 `relative_to` 从 `defined_text_01`…`04` 变成 `exif` |
| ParamCapsule/default.yaml、no_custom_text.yaml | 四个元素的 `margin_bottom` 从 `0.1605` 被三位小数控件量化为 `0.161` |

前者会改变布局依赖和渲染结果，不能当作等价重构的可接受基线。后者是现有精度损失，应单独列明修复或保留策略。

另有模型层遗漏：相对预定义文本的 `line_alignment: right` 经 `from_yaml_dict → to_yaml_dict` 后消失，原因是 `to_yaml_dict()` 第 469 行只在绝对分支写出它；相对 info_position 元素同样在第 435–446 行漏写。`STYLE_GUIDE.md:642` 明确该字段与定位模式无关。内置样式没有覆盖这个组合，必须加入合成样本。

**修订要求：** 在原模型 round-trip 之外增加真实控件 load/save 往返；引用选项必须包含实际元素和预定义文本实例键，并处理增删、改名及未知键的保留/提示。已存在的数据损失单列正确性修复，不能要求其永远保持。区分“重构前后规范化输出一致”与“源 YAML 无损保存”；本次 14 个样式中 12 个在原 YAML → 模型这一步就有语义字典变化（含默认值补齐与省略，不全是缺陷），原文件字节一致更不能直接保证。

### R5 / P2：G1 的统一方案没有定义差异边界，与排版约束冲突

原报告位置：G1 动作、第 205 行、T3/T4。

复用定位语义成立，但现有编辑器的可见结构不同：`ElementEditor` 是单字段每行的两列网格，Logo/CustomText 是两个字段并排的四列网格；Logo 没有文字树 `tree_align` 控件，而 CustomText 有独立行距/行对齐控件。直接把现有 ElementEditor 当成唯一布局复用，会改变 Logo/CustomText 的位置和高度，违反“只有 G10 可以出现排版差异”的约束。

实际交互规则也不相同：无效 cross 值在方向切回 `below` 时，ElementEditor 重置为 `left`，Logo/CustomText 重置为 `center`（探针已确认）；原报告将三段同步逻辑描述为拷贝，没有记录这个差异。模型默认值、`relative_to` 空值判断及专属字段也需保留各自语义。

**修订要求：** 保留 D1 禁用策略，但定义共享字段绑定/定位参数控制器与页面布局之间的边界；各宿主保留现有列数、字段集合、顺序与默认值。若采用一个可配置编辑器，应明确布局模式和能力配置。文字行对齐、文字树、Logo 尺寸等字段不能无条件塞进所有节点并序列化。方向切换默认策略的统一是额外行为变化，须明确选择，而非标记为等价删重。“903→约400”“每块≤300”应是参考，不能代替职责和依赖验收。

### R6 / P2：G3 的旧配置迁移方案不足以支持文案调整

原报告位置：G3 动作、第 207 行。

`findData(旧值)` 失败后再 `findText(旧值)`，只在旧文案仍是当前选项文本时有效。如果改动文案，存着旧中文的配置无法匹配新文字，恰好遗漏报告想解决的场景。

**修订要求：** 保存明确的历史文本 → 稳定 key 迁移表，再用 `findData(key)` 恢复，未知值采用明确回退。测试应包括旧文本配置在新文案下恢复，不能仅验证新 key 配置在改文案后恢复。按“一个版本后删除”迁移会使跳过该版本的用户仍丢配置；宜长期保留廉价的别名表，或使用明确的配置 schema 迁移版本。

### R7 / P2：G5 事实成立，但 P1 与 T1“零风险”均缺依据

调用 `_build_yaml_config()` 前后，原生 `yaml.dump({'items': [1, 2]})` 从块列表变成 `items: [1, 2]`，`yaml.Dumper.yaml_representers[list]` 确实变化。用专用 Dumper 子类隔离是合理修复。

但现有证据只证明全局格式副作用，未证明活动 GUI 消费者发生数据损坏或功能失败；故建议 G5 定为 P2，并将 P1 优先给 R2/R3/R4。无论级别如何，隔离 representer 都改变进程行为，应验证自身 YAML 输出及普通 `yaml.dump()` 隔离，不能与 G11 等一起称为“零风险纯清理”。

## 3. 建议替换的执行与验收顺序

1. **修订报告并留基线**：固定源码指纹；保存原 YAML、规范化模型输出、真实控件往返输出三层数据。保留 D1/D2/D3；将上述正确性问题加入预期修复差异清单。
2. **独立正确性任务**：相对组入布局与高度刷新；PNG 导出；动态引用保留与相对文字行对齐。分别验证、分别提交。精度量化和作者清空另列明确策略。
3. **小型清理与 Dumper 隔离**：撤回映射页直接删保护；不标注零风险。页面构造与序列化隔离应有验证。
4. **稳定 key 迁移**：固定旧别名表；旧文本、新 key、未知值及跳版本迁移各验证。
5. **共享模型/字段绑定，再拆页面**：T3→T4 保持串行；各节点默认值和宿主网格契约明确后才合并。业务导出服务不以“原样搬运”掩盖已确认故障。
6. **目录收编与局部 helper**：枚举、解析、写回格式和覆盖优先级一起定契约；参考能力化计划，避免新增第二套能力判断规则。

验收矩阵至少补充：

| 场景 | 必须验证的结果 |
|---|---|
| 相机/镜头页首次构造、首次显示、再次显示 | 无 `_table` 初始化异常，CSV 正确加载 |
| 两张列表卡 absolute→relative→absolute，初始加载 relative，多条目 | 两组均纳入布局、字段完整可操作、无覆盖/裁剪，卡片高度与模式策略一致 |
