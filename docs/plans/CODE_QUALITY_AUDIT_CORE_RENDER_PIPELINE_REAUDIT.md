## 2. 应优先修正的实施建议

### R1：Q12 的三个夹持位置不是完全相同的算法

原报告 Q12 及前次复核 §7 都认定三处逻辑相同，原报告 §9 更将其列为“低风险纯内部，像素完全一致”。源码不支持这一承诺：

- `layout_engine.py:362–365,609–610` 使用 `max(left, min(x, right-width))`。元素宽于安全区时，最终固定贴左边。
- `layout_engine.py:581–588,714–723` 使用 `if 左侧越界 / elif 右侧越界`。当左侧尚未越界、右侧越界时，会平移到右边，即使这会让左侧越界。
- 相对定位先处理组合盒，再夹持当前元素；树定位统一平移所有成员。作用对象也不是完全一致。

**实测**：画布 100×100，左右 padding 各 20，元素 80×10，原始左上角 `(30,0)`：

```text
普通元素 calculate_position -> (20, 0)
同尺寸单成员 tree_align 树 -> (0, 0, 80, 10)
```

这不是理论上的舍入误差，而是 **20px 的布局差异**，也与 `apply_tree_positioning` 的“单成员树和普通元素一致”注释矛盾。

**修正建议**：可以立即复用普通盒与相对定位末尾的同一夹持公式；组合盒/整树部分必须先确定“放不下时优先贴哪一边”的契约。若统一为普通盒的左/上优先，超大树的坐标变化须单列为修复差异，不能混入等价重构。

### R2：Q15 的性能方向成立，但“透明组只合成一次”不是严格等价替换

`renderer.py:228–245` 确实为每个矩形分配全画布 RGBA 层，并进行两次模式转换及一次合成。前次复核对术语的纠正正确。

但原报告建议“先在同一个 RGBA 图层累积全部矩形，末尾 composite 一次”，前次复核未审查其整数像素行为。即使用正确的 alpha 合成而不是直接 `paste` 覆盖，组合顺序改变也会改变中间量化。

**Pillow 实测，1×1 像素即可复现**：

```text
不透明背景：(17, 83, 191, 255)
第一矩形：  (231, 31, 7, 2)
第二矩形：  (2, 219, 101, 127)

背景逐次合成两矩形：  (11, 151, 146, 255)
两矩形先合组再合背景：(10, 151, 145, 255)
```

**修正建议**：严格保像素时，先考虑背景只转换一次 RGBA，仍逐矩形按原顺序合成，末尾转回 RGB；再评估保持相同量化步骤的局部 patch 合成。若要改成透明组，明确接受小幅像素差异并覆盖重叠半透明区域。直接把多个矩形 `paste` 到同一透明层还会覆盖底层透明度，不能作为等价实现。

原报告“当前非原子”的判断也缺少外部状态证据：这些图像是函数局部中间结果，并非对共享输出逐步提交。这里主要是内存/性能问题。未做大图基准，不能将推算的内存规模视作实测收益。

### R3：Q4 与 Q13 必须区分 API 命名问题和既定配置语义

**Q4 的命名问题成立，行为缺陷的暗示不成立。** `defer_padding` 同时承担“以后夹持”和“永不夹持”确实不够直白，但矩形不受 padding 约束是设计要求：

- `docs/STYLE_GUIDE.md:260,326,442,616` 明确说明矩形豁免。
- `docs/plans/POSITION_ALIGNMENT_REPAIR_EXECUTION_PLAN.md:1007` 明确把矩形 `defer_padding=True` 不受夹持列为验收项。
- `renderer.py:328–330` 本身注明“跳过 padding 约束”。

因此前次复核“实测证明 padding 对矩形彻底失效”只证明实现了豁免，不能证明功能错误。保留该行为，改清楚接口命名/策略归属即可，不应把它与 Q3 的错误绘制同级处理。

**Q13 的数值差异成立，但不是两个本应同义的单位实现。** `layout_engine.py:116–125` 明确 padding 按比例计算；`docs/STYLE_GUIDE.md:535–536` 明确 margin 的浮点数是比例、整数是像素。`style_manager.py:464–466` 的默认配置实际使用 `margin: 10`，这个兼容要求不是抽象可能性。

实测确认短边 4000 时：padding 整数 10 为 40000px；margin 整数 10 为 10px；margin 浮点 10.0 为 40000px。它说明不同字段的单位规则需要清楚命名和校验，**不授权将两者统一成同一种换算语义**。

原报告其实给出了保留整数像素语义的备选函数，这一备选应改为明确要求。对过大 padding 增加诊断可以单独评估。前次复核的旧脚本测的是最终夹持坐标：实际输出 `(10,0)` / `(3900,0)`，不是其脚本注释猜测的 `(10,10)` / `(40000,40000)`；本次直接读取 `_resolve_margins`，避免把单位换算与最终坐标混淆。

### R4：Q5 的回写缺陷成立，但不能据此删除哨兵说明

`renderer.py:910–917` 修改调用方 `options.logo_filename` 的事实成立，本次也实测复用同一个 options 渲染 Canon、Nikon 时只匹配了一次。

但是 `batch_processor.py:225–227` 的注释保护的是：

```text
""   = 显式禁用 Logo
None = 自动匹配
```

即使自动匹配结果改存局部变量，`current_logo or None` 仍会把“禁用”误变为“自动”。**停止回写并不会让该注释失效。** 原报告 §9 第一步把这段注释与回写一并删除，前次复核维持该步骤，两者都混淆了原因。

应先只修复入参回写；等 Logo 模式边界真正显式化后，再更新/移除这段哨兵说明。不要为此提前删除仍解释有效约定的旧注释。

### R5：Q6 除品牌来源，还遗漏了背景明暗来源

前次复核 §4.3 对原始 Make 与映射后 Make 的区别判断正确；但还缺少另一条可直接改变 Logo 的路径：

- `batch_processor.py:209–212` 使用用户选择的 `bg_fill_type`。
- `gui_pyside/pages/image_processing_page.py:1395–1396` 使用 `bg_key`。
- `renderer.py:779–799,914–917` 会先用样式 `custom_bg_color` 覆盖背景，再使用 `effective_bg_type`。
- 一旦上游成功填入 Logo 文件名，renderer 就不再根据有效背景重选。

因此“用户选白背景，样式覆盖成黑背景，品牌同时有普通/白色 Logo”时，上游提前选择可能固定普通 Logo；收敛到 renderer 则会选择白色 Logo。**这是潜在的现存配色错误及收敛后的预期修复差异，不只是品牌映射风险。**

本次以记录型选择器验证完整 `render_frame` 的决策链，同时以真实 `LogoSelector.auto_match_logo`、受控文件名列表确认普通/白色变体选择。结果分别为 `canon.png` / `canon_white.png`。这里未操作真实 GUI，也未声称完成全品牌全样式回归。

应将最终自动匹配建立在统一的品牌来源与最终有效背景上。显式指定文件和禁用状态仍应保留用户意图。收敛前先锁定这两类语义，避免把修复差异当作重构失败。

### R6：Q14-11 必须处理规范，不能只凭“当前不会读取”删除边界

源码当前只按已知定位键取值，因此去掉 `RECTANGLE_SKIP_KEYS` 过滤很可能不改变今天的输出；这部分静态判断成立。

但它不是没有来源的“伪需求”。`docs/plans/RECTANGLE_GAUSSIAN_BLUR_DESIGN.md:186` 第 11 条明确规定这些矩形字段“构造定位配置时必须剔除”，`renderer.py:113` 正在引用该条。

前次复核宣称相关历史文档内容相符，却没有识别删除建议与该条约定冲突。Logo 路径传入更多字段只说明另一个调用方较宽松，并不自动废除这个边界约定。

**修正建议**：若采用“引擎仅读取已知字段，容许无关字段”的契约，应在重构时同步调整设计说明；或者通过明确定位数据结构一次完成边界转换。不能把“当前运行时无读取”写成“没有设计用途”。本次只记录冲突，未改规范或生产实现。

## 3. 已有二次审查哪些判断可靠

### Q3：错误绘制确实存在，但前次脚本只验证了中间图

前次脚本 `recheck_q3.py` 调用 `_analyze_rectangles` 和 `_draw_rectangles`，只得到背景层，未运行照片粘贴阶段。其中心矩形在普通不透明照片内部，完整渲染后会被照片盖住；“红色采样 1000”本身不能证明最终成品可见。

本次补齐完整 `render_frame`：100×100 蓝色照片，底部扩展 50px，矩形 `bottom-center + top-center`、宽 50 高 20、有效红色、`fill.enabled=false`。最终边框点 `(50,110)` 为红色 `(255,0,0)`，证明真实缺陷；把矩形移到照片中心，最终 `(50,50)` 为蓝色，证明遮挡条件不能省略。

原因与前次复核一致：`renderer.py:583–585` 丢弃无有效层 spec，`810` 仅从保留的 spec 生成跳过名单，`857–859` 让被丢弃的效果栈矩形回流 legacy。

**推荐先做最小修复：按配置是否属于效果栈确定排除名单，与是否有有效绘制层分开。** 无需为了修一个可见 bug，先完成整个矩形模块拆分。后续统一计划应明确分为 legacy / 有效 effects / 被禁用或无效的 effects，最后一类绝不能落回 legacy。

### Q7：承载画布不能删除，前次纠正正确

`renderer.py:839–848` 不仅关乎明暗判断，还建立后续复制、粘贴的 `background`。原报告“唯一意义是让 is_dark_bg 有值”错误。

本次完整渲染无扩展、无圆角的 RGB 图片，高斯需求为 `(False,False,True)`，最终输出与原图逐像素相同，确认该短路实际可达。可以简化占位颜色，但必须保留画布；RGBA、圆角与可见边框需保留既有可见性判定。

`FILL_TYPES` 是公开注册表，“私有属性”措辞确实错误。将 `method` / `text_scheme` 的 schema 判断移回管理器是合理封装建议；项目规则禁止硬编码背景选项，但并未逐字规定公开注册表不得读取，因此“直接违反”比代码证据更强。

### 依赖环：前次新增的挂死风险正确，且应优先于大型拆分

`text_renderer.py:378–387` 向上找根的循环没有 visited 集合；`197–199` 将拓扑排序剩余节点直接补回；`style_manager.py:404–426` 只做各节点字段校验，未拒绝依赖环。

本次构造有实际文本的 `a.relative_to=b, b.relative_to=a`：真实样式校验返回 True；真实渲染循环中的 walk 连续为 `a,b,a,b…`。审计脚本通过 tracing 在第 12 次进入循环时主动中止，避免留下挂死进程。循环状态无其他退出条件，足以确认这里的无限循环。

建议在配置边界拒绝环，并让运行时向上遍历/递归具备有界防御；不能只处理 `_collect_tree_members`。修复时也应覆盖自环、缺失目标及没有可显示文本的情况。

## 4. 定级与论据质量

### R7：严格代码质量标准不等于把所有维护问题标成 P0

991 行值得限制继续增长，矩形分析/绘制混在整帧编排中也值得拆分。但原报告没有比较任何基线 diff，不能据此声称“结构性回归”，更没有证据显示 Q1/Q2/Q4 是阻断全体用户的紧急事故。

技能强调的是未经合理解释的规模增长、职责泄漏和复杂度，不是“接近 1000 行即 P0”。颜色解析、蒙版、单矩形绘制实际位于模块级，也不是全由 `FrameRenderer` 类承担。前次复核虽然纠正了行数，却保留了失衡定级，甚至把 Q3 的条件性错误绘制当成更支持 P0 的依据。

建议区分工作优先级：

- **P1 正确性修复**：循环依赖导致不终止；效果栈无有效层回流 legacy。Logo 自动模式的有效背景不一致也应在相关修复中处理。
- **P2 维护与契约改进**：停止回写 options、矩形计划边界、颜色解析统一、几何收敛、接口命名。具体排期可按近期修改频率上调。
- **P3 小型清理或待测优化**：低风险死字段、常量风格、尚未实测的大图性能收益。

超大树定位差异属于有条件的行为缺陷；原有样式若依赖旧边界策略，应明确迁移影响。**修 bug 与全面拆分不是同一个前置任务。**
